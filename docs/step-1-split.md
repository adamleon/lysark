# Step 1: engine and course repos

How Lysark works after step 1 of [lysark-v2.md](lysark-v2.md). Written for the author; no
engine knowledge needed.

## Two kinds of repo

- **The engine** (`adamleon/lysark`, this repo) holds everything that makes slides run: the
  runtime, the scenes and widgets, the slide compiler, and the `lysark` command. Its own test
  lecture is `lectures/demo/`.
- **A course repo** (for example `adamleon/ais2105-lectures`) holds only lectures. Each lecture
  is a folder in `lectures/` with a `slides.md`. A course never contains engine code.

A course uses one fixed engine version, named by a tag such as `v2.0.0`. Engine changes reach a
course only when its version is changed, so a course never breaks because the engine changed
underneath it.

## The `lysark` command

The engine provides one command. In a course repo it runs through `npm run` or `npx lysark`.

| Command | What it does |
|---|---|
| `lysark dev [lecture]` | Live preview in the browser; reloads on every save. With several lectures and no name given, it shows a list to pick from. |
| `lysark build [lecture...]` | Builds each lecture's student file into `dist/<lecture>.html`. Without names, builds all. |
| `lysark check <file.html>` | The offline check: opens the file from disk in Chromium, steps through every slide, and fails on any error or network request. |
| `lysark pdf <file.html>` | Makes the PDF next to it. |
| `lysark site`, `site-pdf`, `site-status` | Used by the course's CI to publish (below). |

`check`, `pdf`, and the `site` commands need Chromium. CI installs it; on a laptop it's only
needed to run them by hand: `npx playwright-core install chromium`.

## How a lecture becomes one file

`lysark build` reads the lecture's `slides.md`, finds which scenes the slides name
(`scene: agilus`), and builds a page that contains only those scenes, the compiled slides, and
the engine. Everything is packed into one HTML file with no outside references, so it opens
offline from disk. A scene name the engine doesn't have stops the build with a message naming
the slide.

Before step 1, each lecture had a hand-written `deck.ts` listing its scenes. That file is now
generated by the build, in memory, from the `scene:` names.

## Publishing (course CI)

Every push to `main` in a course repo runs **Publish lectures**:

1. It reads `versions.json` from the live site, which records the version of each lecture there.
   A lecture's version is computed from its folder, `assets/`, and `package-lock.json` as
   committed.
2. Lectures whose version matches the live site are copied from it unchanged.
3. Changed lectures are built and offline-checked. The site is published with their new HTML.
4. Then the PDFs for the rebuilt lectures are made, and the site is published again.
5. If any lecture failed, the run ends with a red ✗. A lecture that fails keeps its previous
   version; if it was never published, it stays off the index.

The index page lists each lecture with **Open** (for presenting), **Download** (the same file,
saved to disk for offline use), and **PDF**.

Only one run happens at a time: a push made during a run waits for it. The PDF part gives way:
if a newer commit is waiting, it skips the remaining PDFs, and the next run makes them.

Two safety rules:

- If the live site can't be read (a network error or a GitHub Pages outage), the run publishes
  nothing rather than guessing. Only a site that doesn't exist yet counts as a first publish.
- To publish again without a new commit, use **Run workflow** in the Actions tab. Re-running an
  old run is refused once `main` has moved on, because it would put older lectures back.

## Changing a course's engine version

The version is pinned twice: by tag in `package.json`, and by exact commit in
`package-lock.json`. npm follows the lockfile, so editing only `package.json` changes nothing.

Use the course's **Update engine** workflow: Actions tab, **Update engine**, **Run workflow**,
type the tag. It updates both files, commits them, and starts a publish, which rebuilds every
lecture with the new engine. On a computer with npm, `npm install github:adamleon/lysark#<tag>`
followed by committing both files does the same.

## Releasing a new engine version

1. Make the change in the engine repo and push it to `main`. The engine's CI typechecks, runs
   the tests, builds the demo lecture, and offline-checks it.
2. When the CI is green, tag it: `git tag v2.1.0` and `git push origin v2.1.0`.
3. Run **Update engine** in each course that should get it.

## Developing the engine against a course lecture

The course's `npm run dev` uses the pinned engine, so it won't show engine changes in progress.
Clone the engine next to the course and run the engine's dev server on the course's lecture:

```
npm run dev -- ../ais2105-lectures/lectures/baneplanlegging
```

## Why the engine is set up the way it is

Three npm details shape the engine's `package.json` (lysark-v2.md §3):

- A course installs the engine from GitHub, and then gets only the engine's `dependencies`, not
  its `devDependencies`. So Vite, the compiler's libraries, and `playwright-core` are
  `dependencies`.
- The engine has no script named `build`, `prepare`, `prepack`, `preinstall`, `install`, or
  `postinstall`. With any of those, npm would build the engine during every course install.
- `playwright-core` downloads no browser when installed, unlike the `playwright-chromium` used
  before, so laptops never download Chromium by accident.

The `lysark` command itself is plain JavaScript, because Node won't run TypeScript from inside
`node_modules`. The TypeScript parts are loaded through Vite, which compiles them as it goes.
